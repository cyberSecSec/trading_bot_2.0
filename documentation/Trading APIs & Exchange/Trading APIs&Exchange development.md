## Введение

Документ описывает интерфейсы компонента Trading APIs & Exchange для взаимодействия с другими модулями системы VANTA. Компонент обеспечивает единую точку взаимодействия с биржами, абстрагируя специфику различных API и предоставляя унифицированный интерфейс для работы с рыночными данными и выполнением торговых операций.

## Роль и ответственность

Trading APIs & Exchange выполняет строго определенную роль в архитектуре системы VANTA:

- Предоставляет унифицированный доступ к API биржи через четко определенные интерфейсы
- Служит как "тонкий" клиент-прокси для доступа к рыночным данным и торговым операциям
- Управляет соединениями с биржей и обеспечивает их надежность
- Нормализует данные, полученные от биржи, в стандартный формат
- НЕ занимается хранением исторических данных
- НЕ выполняет агрегацию или сложную обработку данных

## Разделение ответственности с другими модулями

### Четкое разграничение ответственности

1. **Trading APIs & Exchange:**
   - Обеспечивает прямой доступ к API биржи
   - Предоставляет унифицированные интерфейсы для доступа к рыночным данным
   - Управляет соединениями с биржей (HTTP и WebSocket)
   - Нормализует данные, полученные от биржи
   - Обрабатывает ошибки соединения и восстанавливает его при сбоях

2. **Data Acquisition and Storage:**
   - Хранит исторические и текущие данные
   - Осуществляет агрегацию и обработку данных
   - Вычисляет производные метрики
   - Предоставляет комплексные рыночные снапшоты
   - Реализует кеширование данных

### Логика агрегации в Data Acquisition and Storage

Data Acquisition and Storage реализует собственный интерфейс IMarketDataAggregator для предоставления агрегированных данных:

**Основные методы IMarketDataAggregator:**
- `get_aggregated_orderbook()` - Получение агрегированного стакана ордеров
- `get_aggregated_trades()` - Получение агрегированных сделок
- `get_liquidation_history()` - Получение истории ликвидаций
- `get_market_snapshot()` - Получение комплексного снимка рынка

## Основные интерфейсы

### Интерфейсы для модуля Data Acquisition and Storage

#### 1. Интерфейс для доступа к данным через REST API (IMarketDataRestProvider)

**Основные методы:**
- `get_klines()` - Получение исторических OHLCV данных
- `get_orderbook()` - Получение текущего стакана ордеров
- `get_recent_trades()` - Получение последних сделок
- `get_open_interest()` - Получение текущего открытого интереса
- `get_open_interest_history()` - Получение истории открытого интереса

#### 2. Интерфейс для доступа к данным через WebSocket (IMarketDataStreamProvider)

**Основные методы:**
- `subscribe_to_klines()` - Подписка на обновления OHLCV данных
- `subscribe_to_orderbook()` - Подписка на обновления стакана ордеров
- `subscribe_to_trades()` - Подписка на новые сделки
- `subscribe_to_liquidations()` - Подписка на ликвидации
- `unsubscribe()` - Отмена подписки

#### 3. Объединенный интерфейс (IMarketDataProvider)

Объединяет функциональность REST и WebSocket интерфейсов.

### Интерфейсы для модуля Operation Layer

#### 1. Интерфейс для торговых операций через REST API (ITradeRestExecutor)

**Основные методы:**
- `create_order()` - Создание нового ордера
- `cancel_order()` - Отмена ордера
- `get_order()` - Получение информации об ордере
- `get_position()` - Получение информации о позиции
- `get_balance()` - Получение баланса

#### 2. Интерфейс для торговых операций через WebSocket (ITradeStreamExecutor)

**Основные методы:**
- `subscribe_to_order_updates()` - Подписка на обновления ордеров
- `subscribe_to_position_updates()` - Подписка на обновления позиций
- `subscribe_to_balance_updates()` - Подписка на обновления баланса

## Рекомендации по методам доступа к данным

### Данные для доступа через WebSocket

| Тип данных | Обоснование | Приоритет |
|------------|-------------|-----------|
| Стакан ордеров | Мгновенное обновление для детекции манипуляций | Критический |
| Сделки | Реалтайм для расчета дельты и анализа | Высокий |
| Ликвидации | Триггеры для детекции манипуляций | Высокий |
| OHLCV (1m) | Базовые данные для алгоритмов | Высокий |

### Данные для доступа через REST API

| Тип данных | Обоснование | Частота запросов |
|------------|-------------|------------------|
| OHLCV (5m+) | Не требуют мгновенной реакции | Раз в минуту или реже |
| Открытый интерес | Используется для контекстного анализа | Раз в 1-5 минут |
| Исторические данные | Нужны при запуске или для анализа | Разово или по требованию |

### Описание компонентов

#### 1. Core (Ядро)

Содержит базовые компоненты модуля:

- **client.py** - Определяет базовый интерфейс клиента для взаимодействия с криптобиржами
- **config.py** - Классы для конфигурации клиента (API ключи, настройки соединения)

#### 2. Connection (Соединения)

Отвечает за управление соединениями с биржей:

- **connection_manager.py** - Центральный компонент, управляющий всеми соединениями
- **websocket_manager.py** - Компонент для управления WebSocket соединениями
- **reconnection_handler.py** - Логика переподключения при сбоях связи

#### 3. Exchanges (Биржи)

Содержит низкоуровневые компоненты для работы с конкретными биржами:

- **bybit/** - Директория для компонентов Bybit
  - **bybit_client.py** - Низкоуровневый клиент для работы с API Bybit
  - **endpoints.py** - Константы с эндпоинтами API Bybit
  - **websocket_handlers.py** - Обработчики WebSocket событий Bybit

#### 4. Models (Модели данных)

Определяет структуры данных, используемые в модуле:

- **market_data.py** - Модели данных для рыночной информации (OHLCV, стакан, сделки и т.д.)
- **trade_data.py** - Модели данных для торговых операций (ордера, позиции и т.д.)

#### 5. Interfaces (Интерфейсы)

Определяет контракты для взаимодействия с другими модулями:

- **market_data.py** - Объединенный интерфейс для получения рыночных данных (IMarketDataProvider)
- **market_data_rest.py** - Интерфейс для получения рыночных данных через REST API (IMarketDataRestProvider)
- **market_data_stream.py** - Интерфейс для получения рыночных данных через WebSocket (IMarketDataStreamProvider)
- **trade_executor.py** - Объединенный интерфейс для торговых операций (ITradeExecutor)
- **trade_executor_rest.py** - Интерфейс для торговых операций через REST API (ITradeRestExecutor)
- **trade_executor_stream.py** - Интерфейс для торговых операций через WebSocket (ITradeStreamExecutor)

#### 6. Services (Сервисы)

Содержит реализации интерфейсов для конкретных бирж:

- **bybit/** - Сервисы для Bybit
  - **market_data_rest_service.py** - Реализация REST API для рыночных данных Bybit (BybitMarketDataRestProvider)
  - **market_data_stream_service.py** - Реализация WebSocket для рыночных данных Bybit (BybitMarketDataStreamProvider)
  - **trade_executor_rest_service.py** - Реализация REST API для торговых операций Bybit (BybitTradeExecutorRestProvider)
  - **trade_executor_stream_service.py** - Реализация WebSocket для торговых операций Bybit (BybitTradeExecutorStreamProvider)

#### 7. Utils (Утилиты)

Вспомогательные компоненты:

- **logger.py** - Утилиты для логирования
- **validators.py** - Валидаторы данных

#### 8. Корневые файлы

- **exceptions.py** - Определения кастомных исключений модуля
- **__init__.py** - Инициализация пакета и экспорт публичного API

### Взаимодействие компонентов

1. **Внешние модули** (Data Acquisition and Storage, Operation Layer) взаимодействуют с Trading APIs & Exchange через **интерфейсы**, определённые в директории `interfaces/`.

2. **Интерфейсы** реализуются **сервисами** для конкретных бирж, которые находятся в директории `services/`.

3. **Сервисы** используют **компоненты соединения** для взаимодействия с биржей и **низкоуровневые компоненты биржи** для формирования специфичных запросов.

4. **Компоненты соединения** управляют HTTP и WebSocket соединениями с биржей, обеспечивая надёжность и отказоустойчивость.

5. Все данные, передаваемые через интерфейсы, соответствуют **моделям данных**, определённым в директории `models/`.

### Принципы проектирования

Архитектура модуля Trading APIs & Exchange следует следующим принципам:

1. **Разделение ответственности** - каждый компонент имеет чётко определённую зону ответственности
2. **Инверсия зависимостей** - высокоуровневые модули зависят от абстракций, а не от конкретных реализаций
3. **Открытость/закрытость** - модуль открыт для расширения, но закрыт для модификации
4. **Модульность** - компоненты слабо связаны и могут быть заменены или модифицированы независимо
5. **Асинхронность** - все операции выполняются асинхронно для обеспечения высокой производительности

Эта структура обеспечивает гибкость, расширяемость и чёткое разделение ответственности, что облегчает разработку, тестирование и поддержку модуля.
